Why this matters for the UI

Several screens need work before this release can ship: sign-in recovery, the KYC form, the artist registration checklist, the booking time picker, payment retry handling and every place that read another user's profile. The checklist lists them in priority order.

new endpoint did not exist in the previous release  ·  changed existing endpoint behaves or returns something different  ·  breaking your current integration breaks unless you update it  ·  multipart sends files (multipart/form-data)

Not available yet (do not build against these)

  • Earnings, payouts, payout history — deferred. Bank details are stored (encrypted) but nothing pays out.
  • Per-kilometre travel charges — only free and per_visit work; per_km is rejected.
  • Marketing Studio content generation and service-styles list — not built yet (waiting on a spec).
  • Logout endpoint — there is none; a session ends when the user logs in elsewhere, the token expires (access 7 days, refresh 30 days), or the client discards it.
  • Account deletion and artist suspension through the API — not exposed.

In priority order — items 1–4 can break existing screens, so do them first.

Behaviour changes that need UI work

  • Prices are server-side. A booking total = package price + selected add-ons + travel fee. Show the returned total_amount; do not compute or send it.
  • Booking slots now include travel/return buffers for Home Visits (see availability endpoint).
  • Approval is stricter: artist needs display name, date of birth, profile type, ≥1 work sample, services, a package, a location type, a weekly schedule, an ID proof, a bank account and the accepted agreement. An admin must verify the ID proof before approving.
  • Editing services no longer un-approves an artist.
  • Customers cannot cancel once the artist has arrived or the service is running.
  • Refunds are real: cancelling a paid booking asks the payment gateway to refund; the customer receives a notification either way.
  • An artist can't book their own services.
  • Notifications have new type values — see Values & limits.

Conventions

The same rules apply to every endpoint: trailing slashes, the response envelope, naming, dates and pagination.

Basics

  • Base URL: {BASE_URL} (per environment). Paths in this guide are relative to it. Every path ends with a slash — leave it out and the request fails.
  • Auth: Authorization: Bearer <access_token> on everything except the “PUBLIC” endpoints. Access token lives 7 days, refresh token 30 days.
  • One session per user. Logging in on another device (or re-logging in) makes the old access token invalid: the next call returns 401 “Invalid access token”. Treat any 401 as “go to login”.
  • Content types: JSON endpoints take application/json. File endpoints take multipart/form-data (badge MULTIPART). Other fields in a multipart request are plain form fields; send lists by repeating the field name.
  • HTTP verbs: GET reads (parameters in the query string), POST creates, PUT updates / performs an action (JSON body), DELETE deletes (id in the query string, no body).

Response envelope

Success:  { "status": true,  "message": "…",  "data": <object | array | {data:[…], presentPage, totalPage}> }
Failure:  { "status": false, "message": "…",  "error": ["…"] }
  • Field names in responses are camelCase (artistId); field names in requests are snake_case (artist_id). Newly created ids come back in snake_case inside data (e.g. {"booking_id": 41}).
  • Money is a string with two decimals ("2500.00") in booking/package/add-on data, except the payment order amount which is an integer in paise.
  • Ids are integers. Missing optional values are null.

Dates, times and time zones

Booking date in requestsDD-MM-YY, e.g. 12-10-26 (create booking, availability, reschedule proposed_date, list from_date/to_date)
Block date, date of birthBlock date accepts YYYY-MM-DD or DD-MM-YYYY; date_of_birth is YYYY-MM-DD
TimesHH:MM:SS (24-hour), e.g. 10:00:00

Files and images

  • Public images: profile/cover photo (profilePhotoUrl, coverPhotoUrl) and package photo (photoUrl) come back as absolute URLs (or null) — use them directly. Portfolio items are the exception: fileUrl is a storage path like portfolios/artist_7/abc.png, so the image is {BASE_URL}/media/<fileUrl>. Admin review photos start with /media/ — prepend the base URL. The public share page already returns absolute URLs.
  • Private files (KYC documents, ticket attachments) are never public. The API returns a route such as /artists/documents/file/?document_id=9; request it with the Bearer header and render the bytes (blob / memory image).
  • Uploads are inspected on the server: the content must really be a JPEG/PNG/WEBP image (or PDF where allowed), the extension must match, and the size limit applies. Failures are 400 with a message — show it.

Money you may show

  • Customer sees totalAmount (includes add-ons and travelFee). Never shown to customers: platformFee, netAmount.
  • Artist sees platformFee (commission) and netAmount on each booking (fixed when the booking was made; null on older bookings).
  • There is no earnings/payout screen data yet.

Retries and double taps

  • Booking creation is not idempotent by itself, but a second identical request is refused (“This slot is already booked”).
  • Payment initiate is idempotent for the same amount (HTTP 200 with the same order). Payment verify is idempotent.
  • Once-only codes (OTPs, booking OTP, PINs) are consumed on success; 5 wrong tries lock the code or account for 30 minutes (message “Account locked. Please try again after 30 minutes”).

Sign-in, passwords and sessions

1

Register

POST /auth/register/ with name, phone_number or email, password, role (customer|artist). Registering as an artist creates the artist profile automatically (exactly one).
2

Or sign in with a code

POST /auth/phone-otp/request/ (add role only for a first-time user) then POST /auth/phone-otp/verify/. Email twin: POST /auth/email-otp/request/ / POST /auth/email-otp/verify/. Codes are 6 digits, valid 10 minutes, single-use; 5 wrong tries lock the account for 30 minutes (403).
3

Password login

POST /auth/login/ with username (email or phone) and password. Google — POST /auth/google/.
4
Every successful sign-in returns, inside data: user_id, name, email, phone_number, role, fcm_token, access_token, refresh_token. Store both tokens securely.
5

Keep the session alive

Before the access token expires call POST /auth/token/refresh/ with the refresh_token; you get a new pair (old ones stop working).
6

Forgot password

POST /auth/forgot-password/ (username) → always 200 → user enters the code → POST /auth/reset-password/ (username, otp, new_password). The password rules are the same as registration. After success all sessions are revoked: go to login.
Handle these: 401 anywhere → clear tokens, show login · 403 on sign-in → account deactivated (or locked 30 min after too many wrong codes) · 400 with error[0].password → weak password (show it).

1

Payment and refunds

flowchart TD
  I["POST payments/initiate"] -->|"201 new order / 200 same open order"| R["Razorpay Checkout"]
  R --> V["POST payments/verify"]
  V -->|"captured, within total"| PD["paid"]
  V -->|"would exceed total"| F["400 + failed, refund by support"]
  PD --> CF["Artist can confirm"]
  CF -->|"booking cancelled later"| RF["Gateway refund requested"]
1
POST /customers/payments/initiate/ with booking_id (full payment) — or with amount and payment_type = advance/balance for part payments. Optional redemption_tier_id to pay part with coins (tiers from GET /customers/wallet/eligible_tiers/).
2
Open Razorpay Checkout with the returned gateway_order_id, razorpay_key_id, amount (paise), currency. If the response has fully_covered_by_coins: true there is nothing to pay — the payment is already settled.
3
When Checkout succeeds call POST /customers/payments/verify/ with razorpay_order_id, razorpay_payment_id, razorpay_signature. The server double-checks with Razorpay that the money was really captured.
4
When the booking is fully paid the artist can confirm it. History: GET /customers/payments/get_all/.
Rules that now exist
  • Tapping Pay twice returns the same order (HTTP 200 instead of 201) — use it, don't create another.
  • If an open order already covers the dues, a different-amount order is refused: “A payment for this booking is already in progress…”. Open orders older than 30 minutes stop blocking.
  • A booking can never be settled for more than its total. If a capture would exceed it, verify returns 400 “…exceed the booking total… will be refunded” and the payment is marked failed (support refunds the customer).
  • Refunds: when a paid booking is cancelled (by customer or artist) the server asks Razorpay to refund the cash portion and notifies the customer: refund_initiated (“a refund of ₹X has been initiated”) or refund_pending (“our team will complete the refund”). Coins used are returned to the wallet. Use neutral wording like “refund initiated” — settlement time depends on the bank.

Booking day (artist app)

stateDiagram-v2
  [*] --> pending: customer creates, slot locked 15 min
  pending --> confirmed: artist accepts (after full payment)
  pending --> cancelled: declined, unpaid after 15 min, or customer cancels
  confirmed --> confirmed: on my way, then arrived (OTP)
  confirmed --> in_progress: start PIN
  in_progress --> completed: completion PIN
  confirmed --> cancelled: cancelled before the artist arrives
  confirmed --> no_show: nobody acted 2 h after start
  completed --> [*]
1

Incoming

The artist gets a new_booking_alert and a booking_otp_issued notification. The booking OTP (6 digits) is what they will enter on arrival. GET /artists/bookings/get_all/ lists bookings; each shows platformFee, netAmount, addOns, travelFee.
2

Accept or decline

PUT /artists/bookings/update_status/ with status=confirmed (only after the customer has paid in full; otherwise 400 “…cannot be confirmed until payment has been completed”) or status=cancelled + reason (decline/cancel; a paid booking is refunded).
3

On my way

PUT /artists/bookings/on_my_way/, only within 2 hours before the start.
4

Arrived

PUT /artists/bookings/arrived/ with the booking_otp. Wrong codes are counted (5 → locked 30 min).
5

Start

The customer reads their Start PIN; the artist enters it in PUT /artists/bookings/start_pin/verify/ → booking becomes in_progress.
6

Finish

The customer reads their Completion PIN; the artist enters it in PUT /artists/bookings/completion_pin/verify/ → completed (cashback is credited to the customer once).
7

After

Rate the customer with POST /artists/customer_reviews/create/ (once per completed booking; private to artists), and reply to the customer's review with PUT /artists/reviews/reply/.

Steps cannot be skipped or repeated (each returns 400 with a message such as “Artist must be marked as on the way…”). A booking nobody acts on is marked no_show automatically 2 hours after its start.

Customer answers

PUT /customers/bookings/reschedule/respond/ with decision=accepted|rejected. Accepting moves the booking (the slot is re-checked at that moment; if it has been taken the call fails with 400 and the request stays pending so they can reject it). The artist is notified (reschedule_accepted/_rejected).

5
A request lapses to expired after 24 h (or at the original start); cancelling the booking closes it (cancelled). A decided request can't be answered again.
